# 宿舍报修管理系统 — 答辩准备资料

---

## 一、项目概述

**课题名称**：宿舍报修管理系统（前后端分离 + 移动端 APP）

**核心功能**：学生在线报修、管理员审批派单、维修人员接单处理、全流程实时通知、AI 智能辅助

**技术栈定位**：Spring Boot 3 后端 + Vue 3 前端 + Capacitor Android APP

## 三、系统架构

```
┌─────────────────────────────────────────────────────┐
│              前端 (Vue 3 + TypeScript)               │
│  学生端 · 维修端 · 管理端 · 移动端 (Capacitor)       │
├─────────────────────────────────────────────────────┤
│  Nginx / Vite Dev Server                            │
│    反向代理 /api → backend:8080                     │
│            /ws  → backend:8080  (WebSocket)         │
├─────────────────────────────────────────────────────┤
│              后端 (Spring Boot 3)                    │
│                                                     │
│  Controller层 → Service层 → Mapper层 (MyBatis-Plus) │
│                                                     │
│  JWT拦截器 → AuthContext → 权限校验                   │
│  AOP @Log → 操作日志自动记录                         │
│  WebSocket → STOMP 实时推送                          │
│  DeepSeekClient → AI 智能分析                        │
│  GlobalExceptionHandler → 统一异常处理                │
│  SecurityHeaderFilter → 安全响应头                    │
│  TraceIdFilter → 请求追踪                            │
├────────────────────┬──────────────────────────────┤
│    MySQL 8.0       │         Redis 7               │
│  7 张核心表         │   验证码 / 限流 / 幂等性      │
└────────────────────┴──────────────────────────────┘
```

**核心设计原则**：
- 前后端分离：RESTful API + JWT 无状态认证
- 分层清晰：Controller → Service → Mapper，职责单一
- 安全纵深：JWT + 验证码 + 限流 + 安全头 + 脱敏 + 软删除
- 可观测性：traceId 全链路追踪 + 结构化日志 + AOP 审计

## 四、核心功能与数据流

### 4.1 报修工单 6 状态生命周期

```
学生提交 → 管理员受理 → 管理员派单 → 维修人员接单 → 维修完成 → 学生确认
   │          │                                    │            │
   待受理     已派单             维修中              待确认      已完成
   (1)        (2)                (3)                (4)        (5)
   
   └────────── 已取消 (6) ←──────────────────────────────┘
   学生/管理员可在 1-4 状态下撤销
```

状态转换由 `RepairStatusEnum.VALID_TRANSITIONS` 矩阵校验，非法跳转（如 1→5）被拒绝。更新时使用 MyBatis-Plus `@Version` 乐观锁防并发。

### 4.2 完整流程

| 步骤 | 谁操作 | API 端点 | 触发动作 |
|------|--------|----------|----------|
| ① 提交 | 学生 | `POST /api/repair-order` | WebSocket 推送通知给管理员 |
| ② 受理 | 管理员 | `PUT /api/repair-order/accept/{id}` | AI 推荐维修工，自动或手动派单 |
| ③ 接单 | 维修工 | `PUT /api/repair-order/worker-accept/{id}` | 通知学生 |
| ④ 完成 | 维修工 | `PUT /api/repair-order/worker-complete/{id}` | AI 风险评分 + 通知学生确认 |
| ⑤ 确认 | 学生 | `PUT /api/repair-order/student-confirm/{id}` | 通知维修工 |
| ⑥ 评价 | 学生 | `POST /api/repair-feedback` | 1-5 星评分 + 文字评价 |

### 4.3 AI 智能四大能力

| 能力 | 方式 | 说明 | 影响 |
|------|------|------|------|
| **故障分类** | 调用 DeepSeek LLM | 根据标题+描述推荐分类和紧急程度 | 学生一键填入，减少选错 |
| **派单推荐** | 纯规则打分 | 技能匹配(35%)+负载(25%)+效率(25%)+满意度(15%) | 最优分配的算法依据 |
| **验收评估** | 纯规则打分 | 首次报修+同宿舍频繁+非工作时间 | 风险分级，高风险的需人工复查 |
| **数据洞察** | 调用 DeepSeek LLM | 统计数据 → 自然语言分析报告 | 管理员看板趋势解读 |

AI 失败（Key 未配置或网络超时）**不阻塞核心流程**，优雅降级。

## 七、移动端 APP

基于 **Capacitor 8** 构建的 Android 原生混合应用。

**关键文件**：
- `capacitor.config.ts` — appId: com.dormrepair.app, androidScheme: http

## 九、答辩常见问题准备

### Q1: 为什么选 Spring Boot 而不是 Spring MVC 传统项目？
> Spring Boot 内嵌 Tomcat、自动配置、起步依赖，减少配置代码。本项目用了约 20 个 starter，如果是传统 Spring MVC 需要手动配置每个框架的 XML/Java Config，开发效率低。

### Q2: JWT 和 Session 认证的区别？为什么选 JWT？
> Session 需要服务端存储 + Cookie，不适合前后端分离和跨平台（Web + APP）。JWT 无状态，Token 存在客户端，服务端只需要验签。缺点是 Token 无法主动撤销，所以设置了 24h 过期 + 启动时配置刷新。

### Q3: 乐观锁 @Version 是怎么工作的？
> 每次更新时 MyBatis-Plus 自动将 `version` 字段加 1，并在 WHERE 条件中带上旧版本号。当两个请求同时操作同一条记录时，后提交的那个会失败（版本号不匹配），抛出 `OptimisticLockingFailureException`，提示"工单已被其他人操作"。

### Q4: AI 推荐维修工的算法是什么？
> 四个维度的加权打分：技能匹配（35%）=该工人类别完成数/总完成数；负载（25%）=100 - 当前待处理数×25；效率（25%）=固定 50 分；满意度（15%）=历史平均分×20。总分≥80 且领先第二名≥15 分时自动派单。

### Q5: 为什么验证码在 Android 上显示不出来？
> 这是一个踩坑经历：`SecurityHeaderFilter` 设置了 `Strict-Transport-Security` 响应头，Android WebView 缓存后自动将所有 HTTP 请求升级为 HTTPS，但后端没有 HTTPS 服务，所以连接全部失败。解决方案：开发环境移除 HSTS 头，HSTS 只在生产 HTTPS 环境下发。

### Q6: 数据库设计的核心表有几张？关系是什么？
> 7 张表：用户(sys_user)、工单(repair_order)、分类(repair_category)、反馈(repair_feedback)、通知(notification)、日志(operation_log)、公告(notice)。工单通过 user_id 关联学生、worker_id 关联维修工、category_id 关联分类，一对多关系。

### Q7: WebSocket 是怎么实现的？
> STOMP 协议 + SockJS 降级。后端 `WebSocketConfig` 配置端点 `/ws`，连接时验证 JWT Token。状态变更时调用 `SimpMessagingTemplate` 推送到 `/user/{id}/queue/notification`（点对点）或 `/topic/admin/new-order`（广播）。

### Q8: 前端路由权限怎么控制？
> 路由 `meta` 中定义 `requiresAuth` 和 `role`，全局 `beforeEach` 导航守卫检查。无 token 跳登录，角色不匹配弹出"权限不足"并重定向到角色首页。

### Q9: 这个项目相比其他课程设计有什么亮点？
> ① AI 集成（分类/派单/评估/洞察）；② 全流程 WebSocket 实时通知；③ 移动端 Capacitor APP；④ 15 项安全措施；⑤ 146 个自动化测试；⑥ Swagger API 文档；⑦ Docker 一键部署；⑧ AOP 审计日志 + 敏感字段脱敏。
